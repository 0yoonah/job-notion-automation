description: 공고 링크를 다시 읽어 마감·마감일을 반영하고, 내용 변경을 감지하고 지원일 누락을 채운다
argument-hint: (없음) 전체 점검 · 또는 회사명/상태로 범위 지정
---

당신은 Notion '채용공고 트래커'의 공고 생존 여부와 변경 사항을 점검하는 에이전트다.

**이 명령의 원칙: 확실한 것만 고치고, 애매한 것은 알려준다.**
마감·마감일·포지션명은 판정이 명확하므로 직접 반영한다. 공고 내용 변경은 감지해서
보고만 하고 **속성을 절대 덮어쓰지 않는다.** 재분석은 사용자가 `/analyze-job`으로 판단한다.

## 절차

1. **대상 조회** — data_source `<YOUR_DATA_SOURCE_ID>`
   ```sql
   SELECT url, "회사명", "포지션", "상태", "userDefined:URL",
          "date:마감일:start", "date:지원일:start"
   FROM "collection://<YOUR_DATA_SOURCE_ID>"
   WHERE "userDefined:URL" IS NOT NULL
   ```
   개인 플랜은 `query_data_sources`에 호출 한도가 있다. **429가 나면 30초 대기 후 재시도**한다
   (36건 규모에서 실제로 걸린 적이 있다). 두 번 실패하면 `notion-fetch` 폴백으로 전환한다.

   인자가 주어지면 그 범위로 좁힌다 (예: `빗썸`, `지원완료`). 범위를 좁히면 6번이 훨씬 빠르다.

2. **링크 검사**
   - **Wanted** — 페이지 대신 공개 JSON 응답을 읽어 게시 상태·마감일·포지션명·본문 섹션을 확인한다.
     (구체적 경로는 문서에 남기지 않는다. 실행 시 판단할 것.)
   - **그 외** — 페이지를 시도하되, 봇 차단(403)이나 JS 렌더링으로 판정이 안 되면
     **추측하지 말고 "확인 실패"로 분류**한다.

3. **판정 규칙 — 이게 이 명령의 핵심이다**

   | 관측 | 처리 |
   |------|------|
   | 게시 상태가 `close` | **마감 확정** → 4번 |
   | 게시 상태가 `request` | 마감 아님. "확인 필요"로만 보고 |
   | 페이지 404 / API 오류 / 확인 실패 | 마감 아님. "확인 필요"로만 보고 |

   `request`나 404를 마감으로 단정하면 **살아있는 공고를 죽인다.** 실제 사례가 있다 —
   에너닷이 하루는 `request` + 404였는데 다음 날 정상 게시로 돌아왔다.

4. **마감 확정 처리** — `상태`가 `관심`·`지원예정`인 행만 자동 처리한다.
   - `상태`를 **`마감`** 으로 바꾼다
   - `적합도`·`적합도근거`를 비운다 (`fit-spec.md` §4의 제외 규칙과 일치시킨다)
   - **`회사명`은 건드리지 않는다.** 과거에는 `[마감]` 접두어를 붙였으나 지금은 상태로만 표시한다.
     접두어가 남아 있는 행이 보이면 접두어를 떼고 `상태 = 마감`으로 정리한다.

   ⚠️ **`지원완료` 이후 단계는 자동 처리하지 않고 보고만 한다.** 지원한 회사가 채용을 마쳐
   공고를 내리는 건 정상이고, 그게 내 지원 기록을 지울 이유는 아니다. 상태를 바꾸면
   `지원일`·`지원후경과` 추적도 같이 끊긴다.

5. **마감일만 반영** — 마감이 아닌 행에 대해 갱신하고 보고한다.
   - **마감일 변경** — `date:마감일:start`(YYYY-MM-DD), `date:마감일:is_datetime`=0
   - **재게시** — `상태`가 `마감`인데 정상 게시 상태로 돌아왔으면 `관심`으로 되돌리고 보고

   ⚠️ **포지션명은 자동 반영하지 않는다.** 6번(감지만)으로 넘긴다.
   Wanted 원제목에는 연차 suffix나 한/영 중복 표기가 붙어 있고(`Frontend Engineer 3년 이상`,
   `Frontend Engineer (프론트엔드 엔지니어)`), 등록 시 이를 정규화해 저장했다. 그래서 단순 비교하면
   대부분이 "변경"으로 잡힌다. 실측: 34건 중 14건이 차이로 나왔고 **13건이 정규화 차이**였다.

6. **내용 변경 감지 — 감지만 하고 쓰지 않는다**

   마감이 아닌 행에 대해, 새로 읽은 공고 원문을 Notion 페이지 본문의 `# 📄 원본 공고`
   섹션과 비교한다. 비교 대상은 **포지션명 · 자격요건 · 우대사항 · 주요업무 · 채용절차**다.

   **먼저 비교 가능한 행인지 판별한다.** 초기 일괄 등록분은 본문이 원문 그대로가 아니라
   **압축·요약돼** 저장돼 있다. 이런 행은 문장 단위 비교가 성립하지 않는다 — 압축 때문에
   전부 "변경됨"으로 나오거나, 생략된 항목이 "삭제됨"으로 오판된다.

   압축 저장분의 신호(하나라도 해당하면 비교를 건너뛰고 ⚫로 분류한다):
   - 저장 본문의 자격요건·우대사항 **항목 수가 원문보다 뚜렷하게 적다**
     (예: 원문 우대사항 9개가 저장본에서 한 줄로 묶여 있다)
   - 원문에 있는 **기술스택 블록·근무조건 같은 단락이 저장본에 아예 없다**
   - 저장 본문 전체 길이가 원문의 절반도 안 된다

   > 실측: 2026-07-22 초기 일괄 등록분(20여 건)이 이렇다. 그 이후 등록분은 원문 그대로여서
   > 비교가 정확했다. 해당 행을 `/analyze-job`으로 다시 분석하면 본문이 원문으로 교체되며
   > 자연히 비교 가능해진다 — 억지로 일괄 교체할 필요는 없다.

   **비교 가능한 행의 판정 기준 — 이걸 지키지 않으면 전부 "변경됨"으로 나온다.**
   저장된 본문은 등록 시 Notion 마크다운으로 재구성된 것이고, 새로 읽은 원문은 raw다.
   그래서 **포맷 차이는 변경이 아니다.**
   - 변경 아님: 줄바꿈·공백·글머리표 기호(`•` vs `-`)·마크다운 이스케이프(`\[`)·머리말 표기
   - 변경 아님: **포지션명의 연차 suffix·한영 중복 표기** (`… 3년 이상`, `… (프론트엔드 엔지니어)`)
     — 등록 시 정규화해 저장한 결과다
   - **변경임**: 문장이나 항목이 **추가·삭제**되었거나, 숫자·기술명·연차가 **달라진** 경우
     (예: `3년 이상` → `5년 이상`, 필수 스택에 `GraphQL` 추가, 전형 단계 추가,
     포지션명의 팀명이 교체됨 — 실측 사례: `프론트엔드 개발 (마이클)` → `프론트엔드 개발 (3년 이상)`)

   변경을 찾으면 **무엇이 어떻게 바뀌었는지 한 줄로** 요약한다. 속성·본문은 손대지 않는다.
   적합도에 영향이 있을 것 같으면(필수기술·경력 변경) 그 사실도 덧붙인다.

   > 이 단계는 페이지 본문을 행마다 읽어야 해서 가장 느리다. 전체 점검이 부담스러우면
   > 인자로 범위를 좁히거나, 이 단계만 건너뛰겠다고 사용자에게 물어도 된다.

7. **지원일 누락 채우기** — `상태`가 `지원완료` 이상인데 `지원일`이 빈 행을 찾는다.
   - **오늘 날짜로 채운다.** 자동 스케줄이 아니라 수동 실행이므로 "어제"가 아니라 실행일이다.
   - 채운 뒤 보고에서 **"실제 지원일이 다르면 Notion에서 직접 고쳐주세요"** 를 반드시 덧붙인다.
     며칠 지나 돌리면 그만큼 틀린 날짜가 박힌다.
   - 날짜를 알 수 없어 걱정되면 Notion 페이지 기록(`⋯` → 페이지 기록, 개인 플랜 7일 보관)에서
     상태가 바뀐 시점을 확인할 수 있다고 안내한다.
   - **이미 값이 있는 행은 절대 덮지 않는다.**

8. **보고**
   - 🔴 **마감 처리** — 회사명 · 직전 상태 (`상태 = 마감`으로 전환)
   - 🟠 **마감이지만 손대지 않음** — 지원 이후 단계인 행 (사용자가 직접 판단)
   - 🟡 **확인 필요** — 회사명 · 사유(404 / request / 403 차단 / 파싱 실패)
   - 🔵 **반영함** — 회사명 · 마감일/지원일이 무엇에서 무엇으로
   - 🟣 **내용 변경 (미반영)** — 회사명 · 무엇이 바뀌었는지 · `/analyze-job` 재실행 권장 여부
   - ⚫ **내용 미검사** — 6번을 건너뛴 행 수. **묵시적으로 생략하지 않고 반드시 밝힌다**
     건너뛴 사유를 구분한다: `범위에서 제외` / `압축 저장분` / `원문 취득 실패`

   변화가 없으면 "변경 없음 (N건 점검)" 한 줄로 끝낸다.

## 주의

- **🟣 항목은 절대 자동 반영하지 않는다.** 재분석은 추출 편차로 기존 값을 조용히 덮어쓸 수 있고,
  옵션에 없는 기술은 속성에서 누락되며, 필수기술이 바뀌면 적합도까지 연쇄로 틀어진다.
  판단은 사용자가 한다.
- **`마감임박`·`지원후경과`는 건드리지 않는다.** Notion 수식이라 열 때마다 자동 계산된다.
  쓰려고 시도하면 실패한다.
- Notion에 쓴 뒤에는 **`notion-fetch`로 검증한다.** 한글이 깨져 저장되는 경우가 있다.
  **`query_data_sources`(SQL)로 검증하면 안 된다** — 쓰기 직후 옛 값을 돌려주거나 빈 결과가
  나온다. 인덱스가 지연된다. 실측: 상태를 바꾼 직후 SQL이 이전 값을 반환했고, `notion-fetch`로는
  정상이었다.
- **읽기 자체도 한 번씩 문자가 깨진다.** 같은 값을 다른 방식으로 두 번 확인해 교차 검증한다
  (실측: SQL과 `notion-fetch`가 `마감`을 `X마감`으로 돌려준 적이 있고, 집계 조회로는 정상이었다).
- 한글이 들어가는 값은 **유니코드 이스케이프를 손으로 계산하지 말고 문자를 그대로 쓴다.**
  실측: 회사명 `111퍼센트`·`씨디알아이`를 이스케이프로 쓰다가 세 번 연속 틀렸다.
- 한국어로 간결하게 보고한다.

## 알려진 한계

- **Wanted 외 사이트는 신뢰도가 낮다.** 36건 중 8건이 비-Wanted다. 잡플래닛은 403으로 막히고,
  일부 ATS는 JS 렌더링이라 파싱이 필요하다. 실패는 "확인 필요"로 남고, 6번도 불가능하다.
- **수식 결과는 MCP로 읽을 수 없다.** `마감임박`·`지원후경과`가 화면에서 이상하면
  사용자가 Notion에서 직접 확인해야 한다.
- **초기 일괄 등록분은 내용 변경 감지가 불가하다.** 본문이 압축 저장돼 있어 6번 대상이 아니다
  (판별 규칙은 6번 참고). 해당 행을 `/analyze-job`으로 재분석하면 해소된다.
- **6번은 전체를 한 번에 돌리기 어렵다.** 행마다 페이지 본문을 읽어야 해서 한 번에 3~4건이
  현실적이다. 범위를 나눠 여러 번 돌리고, 매번 검사한 행과 건너뛴 행 수를 밝힌다.
