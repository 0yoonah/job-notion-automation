# 적합도 산정 스펙 (Single Source of Truth)

`/analyze-job`(신규 등록 시)과 `/score-jobs`(일괄 재계산)이 **공통으로 참조**하는 점수 규칙.

---

## 0. 이 점수가 무엇이 아닌지

**합격 확률이 아니다.** 실제 합격은 지원자 풀·TO·팀 상황·타이밍 같은 회사 내부 변수에
좌우되고, 그건 공고 텍스트에 나오지 않는다. 예측하려 들면 근거 없는 숫자가 나온다.

이 점수는 **"내 프로필 대비 공고 요건 적합도"** 다. 목적은 하나 —
쌓인 공고를 *어디부터 볼지* 정렬하는 것. 낮은 점수가 "지원하지 말라"는 뜻은 아니다.

규칙은 전부 결정적(deterministic)이다. 같은 프로필 + 같은 공고 → 항상 같은 점수.
LLM의 정성 판단을 점수에 섞지 않는다. 순위가 흔들리면 정렬 기준으로 쓸 수 없다.

## 1. 입력

| 출처 | 값 |
|------|-----|
| `profile.md` | `연차`(정수), `보유기술[]`, `미보유기술[]`(선택) |
| Notion 행 | `필수기술[]`, `우대기술[]`, `경력` |

기술명 비교는 **정규화된 정식 명칭의 완전 일치**로 한다 (DB 멀티셀렉트 옵션명 그대로).
`profile.md`의 보유기술도 반드시 DB 옵션명으로 적는다. 예: `리액트` ❌ → `React` ✅

## 2. 점수 규칙 (0~100)

### ① 필수기술 매칭 — 최대 60점
- 공고 필수기술 `N`개 중 보유 `M`개 → `60 × M / N`, 여기에 아래 **분모 신뢰도**를 적용한다
- `N = 0`(추출 실패·미기재) → **36점** (60의 60%, 중립값)

필수기술 비중이 가장 크다. 필수 요건 미달이 곧 서류 탈락 사유이기 때문이다.

### ② 경력 부합 — 최대 20점
| 조건 | 점수 |
|------|------|
| 공고 `경력`이 `무관`·`신입` 또는 비어 있음 | 16 |
| 내 연차 ≥ 요구 연차 | 20 |
| 요구 연차 − 내 연차 = 1 | 12 |
| 요구 연차 − 내 연차 ≥ 2 | 4 |

`3년+` → 요구 연차 3으로 읽는다. 경력 과잉은 감점하지 않는다.

### ③ 우대기술 커버 — 최대 20점
- 공고 우대기술 `K`개 중 보유 `L`개 → `20 × L / K`, 여기에 아래 **분모 신뢰도**를 적용한다
- `K = 0` → **10점** (중립값)

### 분모 신뢰도 — ①③에 함께 적용

요건이 한두 개만 추출된 공고는 그것만 맞춰도 만점이 나온다. 비율식의 분모가 작기 때문이다.
그러면 **요건을 성실히 적은 공고가 불리해지고**, 점수가 "내 프로필과 맞는가"가 아니라
"공고가 요건을 얼마나 뭉뚱그려 썼는가"를 재게 된다. 정렬 기준으로 쓸 수 없다.

`N = 0`일 때 중립값(36점)을 쓰는 규칙을 **"정보가 적으면 부분적으로 중립"** 으로 연장한다.

```
w = min(1, N / 4)
v = min(1, K / 4)

① = (60 × M / N) × w  +  36 × (1 − w)
③ = (20 × L / K) × v  +  10 × (1 − v)
```

- `N ≥ 4`면 `w = 1`이므로 **기존 계산과 완전히 동일하다.** 대부분의 공고는 영향받지 않는다
- `N = 1`이면 `w = 0.25`. 만점을 받아도 `60 × 0.25 + 36 × 0.75 = 42점`
- `N = 0`은 `w = 0`이 되어 위의 중립값 규칙(36점)과 자연스럽게 이어진다

기준값 **4**는 실측(2026-08-06, 11건)에서 필수기술 추출 개수의 중위값(5)보다 약간 낮게 잡았다.
낮추면 보정이 약해지고, 높이면 정상 공고까지 건드린다. 바꾸려면 §6을 따른다.

> ⚠️ 이 보정은 **추출 누락을 보상하는 장치가 아니다.** 공고에 있는 요건을 DB 옵션이 없어
> 담지 못하면 분모가 줄어 여기서 감쇠되지만, 근본 해결은 옵션을 갖추는 것이다
> (`analysis-spec.md` §2의 옵션 대칭 원칙).

### ④ 감점 — 최대 −20점
미보유 **필수**기술 중 아래 *대체 불가 스택*이 있으면 **항목당 −10** (하한 −20).

```
React Native · Vue · Angular · Flutter
```

프론트엔드에서 이 넷은 다른 스택 경험으로 메울 수 없는 플랫폼/프레임워크라서
별도 감점한다. 그 외 필수기술 미보유는 ①에서 이미 반영되므로 중복 감점하지 않는다.

### 최종
```
적합도 = clamp(round(① + ② + ③ + ④), 0, 100)
```

## 3. 적합도근거 (text)

계산 과정을 한 줄로 남긴다. 점수만 있으면 왜 그런지 되짚을 수 없다.

```
필수 5/6 (미보유: SSR) · 경력 3년+ 충족 · 우대 2/4
필수 2/3 (미보유: React Native) · 경력 3년+ 충족 · 우대 1/2 · 대체불가 미보유 −10
필수 6/6 · 경력 요건 없음 · 우대 2/3
```

형식: `필수 M/N (미보유: …) · 경력 … · 우대 L/K [· 대체불가 미보유 −n]`
미보유가 없으면 괄호를 생략한다.

**분모 신뢰도가 적용된 경우(`N < 4` 또는 `K < 4`) 그 사실을 덧붙인다.** 그러지 않으면
`필수 1/1`이 만점처럼 읽히는데 실제로는 42점만 반영된 상태여서, 근거를 봐도 점수를 되짚을 수 없다.

```
필수 1/1 · 경력 신입 · 우대 1/1 · 분모 보정(필수 N=1, 우대 K=1)
필수 5/5 · 경력 3년+ 충족 · 우대 2/4 (보정 없음)
```

## 4. 계산 대상

- **제외**: `상태`가 **`마감`** 이거나 비어 있는 행. `적합도`·`적합도근거`를 비운다.
- **포함**: 그 외 모든 행.

> 마감 표시 방식이 바뀌었다. 예전에는 `회사명`에 `[마감]` 접두어를 붙이고 `상태`를 비웠으나,
> 이제 `상태 = 마감`으로 표시한다. 그래서 제외 조건이 "상태가 비어 있음"만이면
> 마감된 행에 점수가 다시 채워진다. 빈 상태도 함께 제외하는 것은 과거 데이터 대비용이다.

## 5. 정렬

**전용 뷰를 만들지 않는다.** `적합도` 컬럼만 채워두고, 정렬·필터는 각자 Notion에서
컬럼 헤더로 하면 된다. 정렬 기준을 자동화가 고정해버리면 마감 임박 순으로 보고 싶을 때
방해만 된다.

## 6. 규칙을 바꿀 때

가중치(60/20/20/−20), 대체 불가 목록, **분모 신뢰도 기준값(4)** 을 바꾸면
**기존 점수와 비교 불가**해진다. 바꾼 뒤에는 반드시 `/score-jobs`로 전수 재계산한다.
일부만 새 규칙으로 계산된 상태가 가장 나쁘다 — 정렬이 조용히 틀린다.

**DB 멀티셀렉트 옵션을 추가한 뒤에도 재계산이 필요하다.** 단, 순서가 있다:
옵션만 늘려도 기존 행의 속성값은 그대로이므로, 먼저 해당 공고를 `/analyze-job`으로
재분석해 누락된 요건을 속성에 채운 다음 `/score-jobs`를 돌린다. 이 순서를 뒤집으면
새 규칙이 낡은 데이터에 적용돼 오히려 더 틀린다.
